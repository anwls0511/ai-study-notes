# 아홉 번째 학습: AI와 개발자의 역할 분담

> 목표: AI에게 맡기면 좋은 일과 내가 직접 판단해야 하는 일을 구분한다.

## 오늘의 결론

```text
AI는 생각을 대신하는 도구가 아니라 생각을 확장하는 도구다.
AI에게는 초안, 비교, 체크리스트, 예외 케이스 탐색을 맡기기 좋다.
최종 목표 설정, 판단, 검증, 책임은 개발자가 가져야 한다.
```

## 한눈에 보기

| 역할 | AI가 잘 도와주는 일 | 개발자가 직접 해야 할 일 |
| --- | --- | --- |
| 문제 이해 | 요구사항 요약, 질문 후보 만들기 | 진짜 목표 결정 |
| 설계 | 선택지 비교, 장단점 정리 | 현재 상황에 맞는 선택 |
| 구현 | 코드 초안, 예시, 리팩터링 제안 | 코드 적용과 책임 |
| 테스트 | 케이스 후보, 경계값 제안 | 실제 실행과 결과 해석 |
| 리뷰 | 버그 가능성 탐색 | 최종 승인과 배포 판단 |

## 1. 왜 역할 분담이 필요할까

AI를 잘 쓰려면 "무엇을 시킬까"보다 "어디까지 맡길까"가 더 중요하다.

처음에는 AI에게 전부 맡기고 싶어진다.

```text
이 기능 만들어줘.
이 에러 해결해줘.
이 주제 정리해줘.
```

하지만 이렇게 쓰면 내가 이해하지 못한 결과물을 그대로 받게 될 수 있다.

AI는 속도를 올려주지만, 책임까지 대신 가져가지는 않는다.  
그래서 AI와 개발자의 역할을 나눠야 한다.

## 2. AI에게 맡기기 좋은 일

AI는 넓게 펼쳐서 정리하는 일에 강하다.

```text
요구사항 요약하기
애매한 조건 질문으로 뽑기
구현 선택지 비교하기
테스트 케이스 후보 만들기
코드 리뷰 체크리스트 만들기
문서 초안 작성하기
```

이런 작업은 정답 하나를 맞히는 것보다 생각할 재료를 많이 뽑는 것이 중요하다.

예를 들어 테스트를 만들 때 이렇게 요청할 수 있다.

```text
아래 기능에 대해 테스트 케이스 후보를 만들어줘.
정상 케이스, 예외 케이스, 경계값 케이스로 나눠줘.
각 케이스가 왜 필요한지도 같이 설명해줘.
```

## 3. 개발자가 직접 판단해야 하는 일

AI가 도와줘도 개발자가 직접 판단해야 하는 영역이 있다.

```text
이 기능의 진짜 목표가 무엇인지
어떤 trade-off를 선택할지
이 코드가 우리 프로젝트에 맞는지
테스트 결과를 어떻게 해석할지
배포해도 되는지
```

특히 프로젝트 맥락은 개발자가 더 잘 알아야 한다.

AI가 제안한 코드가 문법적으로 맞아도, 현재 팀 규칙이나 구조와 맞지 않을 수 있다.

```text
AI 제안: 새로운 추상화 추가
현재 상황: 작은 공부 프로젝트라 단순한 코드가 더 적합
```

이럴 때는 AI 답변보다 프로젝트 목적을 기준으로 선택해야 한다.

## 4. 좋은 협업 흐름

AI와 협업할 때는 한 번에 결과물을 받기보다 단계별로 나누는 것이 좋다.

```text
1. 내가 목표를 설명한다.
2. AI가 요구사항과 질문을 정리한다.
3. 내가 방향을 선택한다.
4. AI가 구현 계획이나 초안을 만든다.
5. 내가 코드와 테스트를 확인한다.
6. AI에게 리뷰 관점으로 다시 검토시킨다.
7. 내가 최종 판단한다.
```

이 흐름을 쓰면 AI가 틀려도 중간에 잡을 수 있다.

## 5. 개발 공부에 적용하기

공부할 때도 역할 분담이 필요하다.

AI에게 바로 정답을 물어보면 빠르게 이해한 느낌은 들 수 있다.  
하지만 오래 남지 않을 수 있다.

더 좋은 방식은 이렇게 묻는 것이다.

```text
이 개념을 설명해줘.
그 다음 내가 이해했는지 확인할 수 있는 질문 3개를 만들어줘.
내 답변을 보고 부족한 부분을 알려줘.
```

이렇게 하면 AI는 설명자이자 점검 도구가 되고, 나는 직접 생각하는 역할을 유지할 수 있다.

## 6. 오늘의 정리

AI에게 맡기기 좋은 일은 초안 만들기, 선택지 비교, 체크리스트 만들기, 빠진 조건 찾기다.  
하지만 목표 설정, 맥락 판단, 테스트 결과 해석, 최종 책임은 개발자가 가져야 한다.

AI를 잘 쓰는 것은 AI에게 전부 맡기는 것이 아니라, 내가 판단할 수 있도록 좋은 재료를 빠르게 얻는 것이다.
